Good software engineering is about
making change safe

Every practice we’ll cover — commits, branches, PRs, feature flags, parallel runs — is a different expression of this one idea.

Part 2 · What Git really is

Git is a graph of snapshots. Not a sync tool.

Every commit is a frozen photo of your whole project, plus a pointer to the photo before it. A repo is a graph of these photos. A branch is a name pinned to one of them. That’s the whole data structure.

Why this matters for the thread: a graph is reversible. You can always walk back. That’s the foundation everything below stands on.
current branch: main

Each circle is a commit. Filled rust = your feature branch. Outlined = main. The arrows point to the parent commit — Git always knows where you came from, which is why it can always take you back.

The thing everyone fears

Merge conflicts: when the graph can’t decide.

Two people edit the same lines of the same file on different branches. Git can’t guess which version to keep, so it stops and asks. That’s a conflict — not an error, a question.

Principle 1 · The branch you don’t break

main is sacred.

Nothing reaches main without passing through a locked gate. Tests must pass. A human must review. At any moment, main is shippable.

Principle 2 · The economics of small

Small PRs. Short cycle time.

Same total work. Two ways to ship it.

One big PR 487 lines · open 8 days · nervous reviewer
Seven small PRs ~70 lines each · ~1 day each · reviewable in 15 min

Same total work. The bottom is reviewable, revertable, and shippable at any point along the way.

— a 50-line PR is roughly 10× more likely to be reviewed carefully than a 500-line one.

For the curious · smallness at the limit

Even scary changes break down into small PRs.

Real-world example: you’re renaming user.email to user.email_address — used by twelve services across the company. The instinct is one big PR called rename-everything. The safe move is to split it across sixteen tiny PRs.

Sixteen tiny reversible steps instead of one terrifying one. At every stage the system works. Any single PR can be reverted without taking the others down. The old column lives a long, redundant life on purpose — that’s the cost of safety, and it’s almost always worth paying.

Principle 3 · Decouple deploy from release

Feature flags: ship the code, don’t turn it on yet.

Thread: a flag turns a release into a config flip. Config flips are instantly reversible. You’ve made the change small in time as well as size.
What it looks like
  // the new checkout flow is in production code...
  if (flags.isOn("new-checkout", user)) {
    return renderNewCheckout(user);
  }
  return renderOldCheckout(user);  // ...but only this runs for now

The code is deployed. Zero users see it. Flip the flag for the team — ten people see it. Flip it for 1% of users — collect data. Flip it for everyone — release. Flip it off — instant rollback, no deploy needed.

Why this is profound

For most of software history, “deploying code” and “releasing a feature to users” were the same event — and therefore equally scary. Flags split them in two.

  • · Deploy — engineering act, low-risk, many times a day
  • · Release — product act, scheduled, can be undone
  • · Rollback — one config flip, seconds, no Git

Concrete: the “new checkout” sits dormant in production for two weeks while design polishes copy. Then PM flips it to 5% on Tuesday morning. Conversion dips 0.4%. Flip it off by 10:14. No engineer required.

Principle 4 · The parallel-run principle

Run new code beside old code. Compare. Then switch.

Thread: this is the most ambitious version of the thread. Even a complete rewrite can be made small and reversible if you run it next to the thing it replaces.
The pattern

Same input goes to both. Old answer is what the user sees. New answer is recorded but ignored. Every difference is a bug or a known intentional change. When discrepancies drop to zero, flip the switch: new becomes canonical, old becomes shadow, then old is retired.

The scales of the same idea
  • Smallest scale. A feature flag is a parallel run at one feature: old branch and new branch live in the same binary; the flag picks one.
  • Mid scale. A new API endpoint runs alongside the old; clients migrate; the old one is removed.
  • Largest scale. An entire system replacement — Martin Fowler describes this as incremental legacy displacement. The new system runs in parallel with the old, taking gradually more traffic until the old one can be retired without anyone noticing the day it disappears.

Same playbook from changing a button color to replacing a system that’s older than most of the engineers working on it.

Part 1 · The plan

Every layer of software

Step 2 · The trick that made math possible

Place value: where a digit sits matters as much as what it is.

The same digit means a different amount depending on its column. 7 in the ones place is seven. 7 in the hundreds place is seven hundred. Obvious? Yes — now. It took humans roughly five thousand years to invent.

Step 3, continued · How bits live in matter

Two digits. That’s it.

Why? Because two states are the easiest thing the universe can hold reliably.

Electricity

Voltage high or low.

Magnetism

Magnet pointing up or down.

Light

Light on or off.

Three different physical media. Same encoding. Same bit pattern: 1 0 1 1 0 1 0.

Step 4 · Acting on the bits

Gates: the only verbs a computer knows.

A logic gate takes one or two bits in and gives one bit out. Three is enough to build everything above. Click the A and B cells to toggle inputs; the row matching your inputs lights up.

Got it?

AND — both true. OR — at least one true. NOT — the opposite. These three are universal — any computation a computer can do can be built from them. Including, it turns out, arithmetic. Let’s prove it.
