# Trade ideas and selection

Trade discovery opens the existing options slot. Its header says “Choose up to five trades to check.” Rows show incoming and outgoing players, ownership, position, age, contract salary and remaining years, salary change and resulting payroll. There is no verdict badge on an idea. Checked selections become normal trade cards.

Each idea uses one team-first layout. Participating team logos sit beside the team names on the checkbox’s baseline. The perspective team sends on the left and receives on the right, matching the team order in the heading. Both columns use `foreground/3` surfaces with rounded outer corners, square corners beside the four-pixel gap, and a full-width divider beneath each section label. The row separates its team heading, panels and payroll summary with twelve-pixel gaps; panel headers use eight-pixel vertical padding and their bodies use twelve-pixel padding. “Celtics receive” and “Celtics send” are muted, regular-weight section labels; player names are larger and medium-weight. On mobile, salaries sit below player details so names and contract details can use the full column width. The payroll summary sits below the columns without a divider. Comparison variants and their preview toolbar are removed.

The shared `SelectionGroup` composes the installed shadcn/Base UI FieldSet, Field, FieldLabel and Checkbox. Its controlled value and minimum/maximum support both exact counts and upper limits. The counter stays in the question header. Count validation is shared between canonical backend answers and the composer. Player inspection is a sibling action, never a nested selection button.

Discovery browsing cycles through outgoing packages and trade partners, so broad team searches show different outgoing players from the first page. Searches for named outgoing players keep those players fixed. The browse order maps back to canonical ordinals, preserving existing proposal identities; cursors represent positions in that browse order.

`find_options` creates a versioned search with a pinned roster and optional original scenario. `trade-ideas.ts` enumerates eligible packages and applies requested age, position and financial filters. A page has at most 30 ideas and scans at most 50,000 combinations. `getTradeIdeas` is read-only: paging/search does not change conversation versions or contact the trade validator. A nonterminal cursor remains available even if a page finds no matches. Candidate identity is the saved search version plus an ordinal. The server reconstructs that proposal rather than trusting client-supplied assets.

The end of the list shows “Showing X of Y” using the matching count for the active filter. Spaces of up to 50,000 combinations get a bounded cached local index; larger spaces keep bounded paging and show the loaded count until an exact total is available. Counting never contacts the validator. The thread shows “Waiting for your answer…” whenever a choice picker is open.

The browser retains selections across pages and filters. More ideas load when the end of the list approaches the visible scroll area; the displayed count sits inline at the end without a footer row or “Show more” button. Exact count questions such as three participating teams still require three. For trade ideas, one through five selections are accepted. Plain messages can refine the request or change topic.

The options area measures its original contents once and keeps that height for the question, capped by responsive viewport limits. Small lists stay compact and large lists use the cap; filtering to one or no matches never moves the composer. Viewport changes still update the cap. During a browse request, the previous choices remain visible at reduced opacity and cannot be selected, with a spinner centered over the visible options area. Search and Cancel remain usable. Request versions discard superseded replies; failed requests retain the list and offer a centered retry action. The atlas includes authored loading and error checkpoints using the production component.

Every options header has a ghost “Cancel” button at the right, after any selection counter. Cancelling dismisses the picker and its waiting marker, clears the choices, and preserves the original question in the thread. The transcript shows a muted, right-aligned “No options selected” status in a small bubble with the normal user-message background colour, using the same font, size and colour as the “You selected” receipt label, with italic styling. The request still sends the existing cancellation payload, and the saved user entry carries `cancelQuestionId` through reloads, archives and retries. Its matching successful “Cancelled.” confirmation is hidden from the transcript; errors remain visible. Typed cancellation messages and historical entries without an action marker retain their ordinary message presentation.

The server closes that specific open question inside the ordinary conversation transaction, with version checks and request deduplication. It does not call the model or validator, and existing proposals and search records remain available. Recorded previews support the same dismissal, and the atlas includes live cancellation flows for player choices, team choices and trade ideas.

Selected trades retain their canonical labels in one “You selected” receipt. Each row adds overlapping player portraits using the existing headshots and initials fallback; portraits open player details without changing the selection. Up to three portraits appear per row, with a remaining-player count for larger packages. Labels wrap on mobile. The local `selection-replies` review fixture includes the three Jordan Walsh trades and interactive cancellation.

The composer keeps its standard arrow send button when options are selected. Selecting without additional instructions runs a deterministic server operation: no extra model interpretation, at most three simultaneous validation calls, one call per selected idea. Supplemental text goes through the conversation agent so corrections remain meaningful. Validation uses current authoritative data, preserves every unchanged transfer and scenario assumption, and displays results in selection order. Selected ideas do not execute trades or change roster ownership.

The obsolete background validation runner, SQL search repositories, alarms, permits, polling and progress UI have been removed. Search records, immutable proposal references, ordinary conversation transactions and Unicode-safe storage remain.
