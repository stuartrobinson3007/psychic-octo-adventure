# Historical backend request and result review

This records the 7 October implementation. Search and selection now follow [trade ideas and selection](trade-ideas.md); capability details are in [backend capabilities](backend-capabilities.md).

Reviewed on 7 October 2026 against the implemented Gambit demo, direct OpenAI chat (`gpt-4.1-mini`) and the live bball-GM API. These are synthetic 2026–27 rosters and contracts. A valid result means the submitted package passed that engine's checks for that dataset.

`complete` describes a completed conversation turn; the card's verdict separately says `valid`, `invalid_trade` or `validation_unavailable`. Clarification, research, cancellation and unsupported requests do not create a new card. After an unsupported edit, the existing card can still say Valid: it describes the previous checked proposal.

## Problems found and fixed

The first live baseline passed 15 of 20 assertions. Follow-up stress testing found additional failures.

1. **Clarification lost the original request.** Pending drafts now retain the request text, resolved identities and staged package without overwriting the checked trade.
2. **Salary explanations reversed who sent which player.** These explanations now render directly from canonical transfers and returned engine evidence.
3. **Failed additions could leave a smaller package to validate.** Failed requested edits block the check. Unsupported contract assets stop the request and discard staged edits.
4. **Late model failure could leave partial state.** A turn stages edits and results and commits only after an explicit successful terminal tool.
5. **Removing a player stopped without checking.** A supported trade edit must obtain a verdict before completion. One-way proposals are allowed.
6. **Cross-team replacement searched only the old owner's roster and could drop the other side.** Exact named replacements correct a mistaken search filter. A dedicated atomic replacement tool derives the team pair and retains the other assets. Team selection cannot silently drop an unmentioned player. Conflicting replacement examples in the prompt were corrected.
7. **“Never mind” cleared the checked trade.** Cancel and clear now have separate intents and tools, with distinct permitted actions.
8. **Undo merely rechecked the current package.** Undo must restore an earlier version before it can validate.
9. **Ambiguous removal guessed a player.** Removal identity checks use the request's original assets, preventing a changed draft from making the wrong remaining player appear unambiguous.
10. **Correcting a hallucinated ID left a permanent error.** A subsequent grounded catalogue search and successful addition can supersede that bad ID; failures on actual requested assets remain blocking.
11. **Unavailable verdicts were cached as final answers.** Repeated checks now retry unavailable results while reusing unchanged successful evidence.
12. **Session loss stranded browser follow-ups.** The browser can restore and revalidate its last checked snapshot automatically. Successful clear also clears browser active state.
13. **Fairness questions received salary-validity answers.** Basketball value has its own response and evidence limit.
14. **Composer name conversion changed the user's intention.** “Grant” could become Jerami Grant despite matching another player's first name; ambiguous references now require selection. Nearby short words such as “of”, “to” and “no” are no longer swallowed as name typos.
15. **Unsupported discovery filters looped on an unknown feature.** The classifier now recognizes those filter restrictions and returns the scope explanation directly.
16. **An error response could repeat an unverified model claim.** Failed edits now publish a backend error instead of the model's arbitrary unsupported-response narrative.

Research and explanation intents cannot execute mutation tools. Tool availability is checked on the server as well as supplied to the model. Ordinary model prose cannot finalize a trade; explicit terminal tools publish the result.

- **76 automated tests passed**, including the adapter, agent loop and discovery suites.
- **TypeScript, ESLint and production build passed.** The build still reports the existing large-client-chunk warning.
- **Browser results verified:** valid and invalid cards, exact salary directions, retained assets during cross-team replacement, ambiguous-name selection, clear/fresh lineage and recovery after server session loss.

The batches were rerun as the relevant fixes landed; this is not a claim that arbitrary future wording will always pass.

The automated suite drives the real AI SDK tool loop with a mock model to cover failures that are difficult to reproduce reliably live: late model errors, aborted checks, malformed engine evidence, duplicate requests, concurrent revisions, saved-verdict tampering and session isolation. Live runs exercise actual model interpretation and the actual trade API, and retain full tool traces in temporary JSON reports.

Browser testing used an isolated local origin, keeping the user's existing conversation separate. It covered incomplete request → named reply → valid card, invalid variation, exact salary explanation, session recovery, clear/fresh trade and badge-based cross-team replacement.

## Practical limits

These checks establish behavior for the tested inputs, not every possible natural-language phrasing. The model can still misunderstand an intention; tool guards, explicit failures and unchanged checked state provide containment, and future failures should become regression cases.

This is a single-process demo with in-memory sessions, a two-hour TTL and bounded history. Server restart loses pending clarifications and older undo history; restoring a checked proposal does not restore that history. Multi-worker production would need shared durable session state and coordination.

Live data and model availability remain external dependencies. The tool loop is bounded to 14 steps, 28 calls and 45 seconds. Picks, signing workflows, exceptions, consent, hypothetical contracts, trades with more than four teams and automatic multi-team discovery remain intentionally unsupported. Discovery checks at most 18 shortlist packages and returns up to three options; required hard filters outside its implemented constraints are rejected. During development, editing the custom Lexical node module can invalidate an existing editor through hot reload; a full browser reload restored it during testing. The engine result is not a comprehensive real-world NBA transaction approval or a basketball-value recommendation.
